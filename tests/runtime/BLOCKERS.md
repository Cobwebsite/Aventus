# Points à analyser pour les tests du runtime



- **Ancien sous-objet `Watcher` après remplacement.** Après `model.child = nouveau`, une édition via l'ancien proxy `child` émet encore une notification au chemin `child.count`, alors que l'extraction du modèle contient uniquement la nouvelle valeur. Le test `reactivity.test.mjs` caractérise cette notification résiduelle ; décider si le remplacement doit détacher les anciens proxys et leurs abonnements.
- **Ancien sous-objet `Watcher` après suppression.** Après `delete model.child`, modifier l'ancien proxy continue de notifier l'abonné racine avec le chemin `undefined.count`, alors que `child` n'existe plus dans le modèle extrait. Le test `reactivity.test.mjs` caractérise ce chemin invalide ; décider si le proxy doit être désabonné ou conserver une notification avec un chemin défini.
- **Référence partagée dans un modèle `Watcher`.** Si `left` et `right` référencent le même sous-objet, modifier `left.count` actualise aussi `right.count`, mais ne notifie que `left.count` ; modifier par `right` ne notifie que `right.count`. Après suppression de `left`, `right` continue de fonctionner. Le test `reactivity.test.mjs` caractérise ces chemins ; décider si tous les chemins qui pointent vers la même donnée doivent être notifiés.
- **Changement de signal pendant un `Effect`.** Si le callback d'un effet modifie un signal qu'il vient de lire, l'effet ignore la notification pendant sa propre exécution et ne se relance pas pour cette nouvelle valeur. Le prochain changement externe le relance normalement. Le test `reactivity.test.mjs` caractérise ce résultat ; décider si un second passage doit être programmé après l'exécution courante.
- **`compareObject` ignore `tableOrder: false` pour un tableau imbriqué.** L'exemple de `lib/compare_object.md` attend `true` pour `{ name: "John", todos: ["todo1", "todo2"] }` comparé à la variante dont `todos` est inversé. Dans le bundle compilé, `Aventus.compareObject(first, reordered)` retourne `false` (valeur par défaut `tableOrder = true`) et `Aventus.compareObject(first, reordered, false)` retourne encore `false` ; comparer directement les deux tableaux avec le troisième argument `false` retourne `true`. `CompareObject.lib.avt` transmet `true` à la récursion sur les propriétés d'objet, ce qui perd le choix initial. `RuntimeTools.lib.avt` et `compiled-project.test.mjs` reproduisent ces trois résultats. Corriger la propagation de l'option ou clarifier l'exemple documenté.
- **`Aventus.uuidv4` et `Aventus.sleep` absents du bundle compilé.** `RuntimeTools.lib.avt` référence les deux fonctions documentées par `lib/uuid.md` et `lib/sleep.md` ; la compilation du projet de référence réussit, mais dans Chromium `typeof Aventus.uuidv4` et `typeof Aventus.sleep` valent tous deux `"undefined"`. Un appel direct à `Aventus.uuidv4()` lance `TypeError: Aventus.uuidv4 is not a function`. Le test `compiled-project.test.mjs` caractérise cette absence. Vérifier la sélection des dépendances des fonctions de `base/src/tools/UUID.lib.avt` et `Sleep.lib.avt` lors de la compilation.
- **`Aventus.CallbackGroup` absent du bundle compilé.** `RuntimeCallbackLibrary` utilise `new Aventus.CallbackGroup<(value: string) => void>()` comme dans `lib/callback.md`. Le CLI compile le projet de référence sans diagnostic, mais Chromium lance `TypeError: Aventus.CallbackGroup is not a constructor` lors de l'appel. `Aventus.Callback` est présent et ses abonnements, résultats et retraits fonctionnent dans le même test. `@Dependencies([{ type: Aventus.CallbackGroup, strong: true }])` sur une autre classe compile également mais ne rend toujours pas `CallbackGroup` disponible. Les deux variantes sont caractérisées par `compiled-project.test.mjs`. Vérifier l'inclusion de cette classe depuis `base/src/lib/Callback.lib.avt` et la résolution du décorateur pour une classe de base.
- **Constante racine `.lib.avt` acceptée contrairement à la documentation.** `lib/create.md` indique que les constantes et variables racine sont interdites dans un fichier de bibliothèque. `RuntimeFunction.lib.avt` exporte pourtant `const runtimeNumber = 7` : le CLI compile sans diagnostic, le bundle expose `RuntimeReference.runtimeNumber === 7` dans Chromium, et `server/src/language-services/ts/lib/File.ts` active explicitement `allow_variables: true`. Le test `compiled-project.test.mjs` caractérise ce résultat. Clarifier la règle documentée ou la validation du LSP.
- **`@Required()` documenté pour une classe mais déclaré pour une méthode.** `wc/create.md` conseille `@Required()` au-dessus d'une classe pour forcer son export. Le cas `cases/required-class/RuntimeRequired.lib.avt` suit cette forme ; le CLI échoue avec « Unable to resolve signature of class decorator » et « Decorator function return type ... is not assignable ». `base/src/attributes/Attributes.def.avt` déclare `Required(): AvMethodDecorator`, tandis que le LSP traite le décorateur sur les classes. Le test `compiled-project.test.mjs` vérifie l'échec. Harmoniser la déclaration avec l'usage de classe ou corriger la documentation.
- **Nom `@Dependances` dans `wc/create.md` invalide.** La documentation donne `@Dependances(...)`, mais la déclaration dans `Attributes.def.avt` et `DependenciesDecorator.ts` utilisent `@Dependencies(...)`. Le cas `cases/dependances-doc/RuntimeDependances.lib.avt` reproduit `Cannot find name 'Dependances'` au CLI ; le test `compiled-project.test.mjs` vérifie le diagnostic. Corriger l'orthographe dans la documentation.
- **`clearWatchHistory()` généré par `@Debugger` lance une exception.** Avec `@Debugger({ enableWatchHistory: true })` sur `RuntimeReactivity`, `getWatchHistory()` contient l'état initial puis une entrée après `model.child.count = 8`. L'appel à `clearWatchHistory()` lance `TypeError: this.__watch.clearHistory is not a function` dans Chromium ; l'historique est néanmoins vidé pendant l'accès à la propriété. Le compilateur génère `this.__watch.clearHistory()`, alors que le proxy `Watcher` traite la lecture de `clearHistory` en vidant l'historique sans renvoyer de fonction. `compiled-project.test.mjs` caractérise l'exception et l'état après l'appel. Harmoniser l'API du proxy et le code généré.
- **`Ram.getAll()` renvoie un tableau alors que `ram/crud.md` annonce une collection indexée.** Le tableau « Read » décrit `getAll` comme un objet `{[index]: T}` et l'exemple TypeScript lui assigne `Map<number, RamItem<Person>>`. Dans le bundle compilé du projet de référence, `await RuntimePersonRAM.getInstance().getAll()` renvoie un `Array` contenant les deux personnes, tandis que `getRecords()` renvoie bien un `Map`. `compiled-project.test.mjs` vérifie les formes et les identifiants. Corriger la documentation ou le contrat de retour annoncé.
- **`Aventus.Animation` absent du bundle compilé.** `RuntimeAnimation.lib.avt` construit `new Aventus.Animation({ animate, stopped, fps })` selon `lib/animation.md`. Le CLI compile sans diagnostic, mais `typeof Aventus.Animation` vaut `"undefined"` dans Chromium et l'appel lance `TypeError: Aventus.Animation is not a constructor`. `compiled-project.test.mjs` caractérise ces deux résultats. Vérifier la sélection de `base/src/lib/Animation.lib.avt` parmi les dépendances du bundle ; une fois incluse, vérifier les transitions `start`/`stop` et la cadence de trames.
- **`outsideModule` génère des exports hors de leur portée.** Avec `compile.input = ["./src/RuntimeFunction.lib.avt"]` et `outsideModule = ["./src/RuntimeFunction.lib.avt"]`, le CLI annonce une compilation réussie. Le bundle ferme l'IIFE `RuntimeReference` avant d'émettre `let runtimeNumber = 7; __as1(_, 'runtimeNumber', runtimeNumber);` et les autres exports, mais `__as1` et `_` sont déclarés dans l'IIFE fermée. Dans Chromium, `window.runtimeUpper` et `RuntimeReference.runtimeUpper` sont tous deux absents ; le script s'arrête sur une référence hors portée. `compiled-project.test.mjs` vérifie la position du code et l'absence des exports. La documentation `config/build.md` promet l'accès via `window.Test`.
- **`namespaceStrategy` ne crée pas les namespaces configurés.** Dans une copie du projet, définir `namespaceStrategy: "followFolders"` ou `"followFoldersCamelCase"` avec `namespaceRoot: "./src"`, ou `"rules"` avec `namespaceRules: { "Configured": ["./src/RuntimeNamespace/*"] }`, au niveau de la configuration et du build, puis sélectionner `./src/RuntimeNamespace/RuntimeScoped.lib.avt` comme entrée. Les trois builds réussissent, mais Chromium expose toujours `RuntimeReference.RuntimeScoped.name() === "scoped"` à la racine ; `RuntimeReference.RuntimeNamespace` et `RuntimeReference.Configured` sont absents. `compiled-project.test.mjs` vérifie les trois modes. `Build.getNamespaceForUri()` calcule un namespace à partir du chemin, mais aucun appel depuis la compilation des fichiers source n'apparaît dans le LSP. La documentation `config/build.md` décrit ces stratégies comme générant un namespace depuis le dossier ou les règles.
